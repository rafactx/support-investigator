# The policy gate derives `diagnosis.confidence` deterministically from observed evidence; the model's own confidence claim never reaches `final`

Building the structured `InvestigationResult` and policy gate required deciding what `evaluatePolicy` actually takes as input. The `InvestigationResult` contract gives the model a `diagnosis.confidence` field to fill in, and CONTEXT.md's `Confidence` entry already states a formula for it ("2+ consistent evidences → high; one operational + one documental → medium; hypothesis only, no direct evidence → low"). Trusting the model's own self-reported `confidence` value and only gating on it would have made "final authority" (ADR-0006) a fiction: an LLM asked to self-assess confidence is exactly the kind of overconfidence ADR-0006 exists to guard against, and a live run against Bedrock during this work proved the risk is real, not hypothetical — the model proposed `confidence: "high"` for both the ADR-0006 flagship case (one `simulate_fulfillment` + one `search_support_knowledge` evidence, ADR-0006's own pinned `medium` example) and for a ticket with zero evidence at all (missing `orderId`, CONTEXT.md's pinned `low` case).

We chose to have `evaluatePolicy` (`src/domain/policy-gate.ts`) compute `confidence` itself from the `evidence[]` it's given, via a private `deriveConfidence` function, and ignore whatever confidence the model proposed. This meant `PolicyGateInput` could not be an `InvestigationResult` — the contract's `diagnosis.confidence` field has no room for "the model's guess, to be overridden," and the `InvestigationResult` Zod schema matches that contract exactly, which rules out adding one. `PolicyGateInput` is therefore its own type: `evidence`, `missingInputs`, and `toolFailures` are facts the orchestration layer is expected to have observed directly (not the model's self-report), while `hypothesis`/`summary`/`recommendedActions`/`citations` are prose the gate has no way to derive on its own and simply carries through unchanged into `final`. The CLI's `investigate` command builds this input from the model's `proposed` result for `evidence`/`missingInputs`/prose (there is no independent observer of those yet) but always passes `toolFailures: []` — real tool-failure observation, independent of the model's own report, belongs to the eval harness (its 3 permission/403 golden tickets), not fabricated here.

`deriveConfidence` classifies each `Evidence` by its `source` rather than storing a `kind` field on the evidence item itself (which the exact-contract constraint also forbids): `get_order_context` and `simulate_fulfillment` are "operational" (direct, case-specific facts about this ticket); `search_support_knowledge` is "documental" (general support documentation, not case-specific — CONTEXT.md's `Confidence` entry calls this "no direct evidence"). CONTEXT.md names exactly three points on this scale (2+ operational → high; 1 operational + 1 documental → medium; zero evidence → low) but leaves gaps — a single lone operational evidence with no corroboration, or documental evidence alone with no operational evidence at all. Both gaps fall to `low`: the same conservative bias ADR-0006 states outright ("false confidence in a support tool is worse than an extra escalation") extended to the two cases CONTEXT.md's three examples don't cover.

Rule precedence in `evaluatePolicy` — missing input, then tool failure, then confidence — is evaluated in that fixed order and the tool-failure rule fires unconditionally, overriding even evidence that would otherwise derive `confidence: high`; ADR-0006 lists "a required tool failed → `needs_human`" with no confidence qualifier, so a partially-successful investigation with strong evidence still can't self-resolve if one of the tools it needed came back broken. `policy-gate.sabotage.test.ts` proves this precedence is actually enforced by CI-shaped tests, not just implemented: it runs the identical rule-table assertion battery against the real `evaluatePolicy` (green) and against a saboteur that resolves at `confidence: medium` too (red), rather than hand-asserting a wrong value once and calling it a sabotage test.
