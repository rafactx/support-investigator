# Permission-denied gets its own `OrderAccessDeniedError`, not a reused `OrderNotFoundError`; the tool-activity observer doesn't discriminate the underlying cause

Building the eval harness's permission-403 golden tickets (the testing plan calls for "3 permission/403 cases") required a real, gateway-level failure mode to exercise end to end — the `needs_human` rule ADR-0006 states for "a required tool failed (e.g. a 403)" had unit-test coverage in `policy-gate.test.ts` but no fixture path that actually produced a tool failure through the real `Agent` → `McpClient` → Support MCP → `CommerceGateway` chain. `OrderNotFoundError` already existed and could have been reused (a 403 is, after all, "the order didn't resolve"), but the two are semantically different outcomes with different next actions: a not-found order is a normal, expected dead end (wrong order id, typo, order genuinely doesn't exist) — nothing to escalate about; a permission denial means the platform refused the agent's own credentials, which is exactly the "the platform is down"/"access denied" case ADR-0006's `needs_human` rule exists to force a human into, never silently treat as an empty result.

We added `OrderAccessDeniedError` (`src/gateway/commerce-gateway.ts`) as its own error class, and a `FORBIDDEN_ORDER_IDS` set (`src/gateway/fixtures/orders.ts`, `ORDER-4031`/`4032`/`4033` — the ids the golden tickets and `mcp/server.test.ts` now use) that `createFixtureCommerceGateway.getOrder` checks *before* falling through to the normal `FIXTURE_ORDERS` lookup, so a forbidden id never resolves to `OrderNotFoundError` even though it also isn't in the fixture map. The MCP tool layer's existing default error handling (`@modelcontextprotocol/sdk`'s `createToolError`) turns any thrown error into `{ content: [...], isError: true }` without needing a new code path — `OrderAccessDeniedError`'s distinct message (`Order access denied: ...`, asserted in `mcp/server.test.ts` to not contain "not found") is what a caller (or a test) actually distinguishes on.

The harder call was `src/evals/tool-activity.ts`'s `extractToolActivity`, the independent observer `run-eval-suite.ts` uses to build `evaluatePolicy`'s real `toolFailures` (as opposed to the model's own self-report — the gap ADR-0010's CLI doc comment left to the eval harness). It could, in principle, inspect the error text and classify *why* a tool failed (403 vs 500 vs timeout) before deciding whether it counts as a `ToolFailure`. We chose not to: every `ToolResultBlock` with `status: 'error'` for a Support MCP tool becomes a `ToolFailure`, unconditionally, regardless of cause. ADR-0006's rule itself has no cause qualifier ("a required tool failed", full stop), and the MCP SDK's own error-wrapping already collapses every thrown error into the same `isError: true` shape at the wire level — there is no reliable, non-brittle signal left in a `ToolResultBlock` to discriminate a real 403 from an `OrderNotFoundError` from an unexpected bug, short of string-matching the message, which would silently break the moment error text changes. Treating every tool error as evidence of a failure worth escalating is the same conservative bias ADR-0006 and ADR-0010 already commit to ("false confidence in a support tool is worse than an extra escalation") extended one level down, to the observer that feeds the gate rather than the gate itself.
