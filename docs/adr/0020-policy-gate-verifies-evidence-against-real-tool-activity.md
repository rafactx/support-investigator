# The policy gate's evidence is verified against real tool activity, not taken on the model's word

An independent code review found the gate's central claim — that it has "final authority" over `status` because `missingInputs`, `toolFailures`, and `evidence` are facts the orchestration layer observed directly (`PolicyGateInput`'s own doc comment) — was only true for `toolFailures`. `investigate.ts` and `run-eval-suite.ts` both built `evaluatePolicy`'s `evidence` input from `proposed.evidence`, the model's own self-report, with nothing checking it against `extractToolActivity`'s independently-observed `calledTools` (which was already computed for `toolFailures` and simply never cross-referenced). Concretely: a model could self-report two `Evidence` items citing tools it never called and still derive `confidence: high` → `status: resolved` — the exact "false confidence" outcome ADR-0006 exists to prevent, and undetected by any existing test, since `policy-gate.test.ts`/`policy-gate.sabotage.test.ts` only ever exercise `evaluatePolicy` directly with hand-built, already-trusted input.

`verifyEvidence` (`src/agent/tool-activity.ts`) now filters `proposed.evidence` down to items whose `source` tool appears in `calledTools` before it ever reaches `evaluatePolicy`, in both call sites. This closes the reviewed reproduction case but not every case: `calledTools` is deduped by tool name (proves "this tool ran at least once", not that each individual evidence item traces to a specific real call), so a model could still pad a genuinely-called tool with extra fabricated evidence under its name. A full fix would need to match each evidence item to a specific `toolUseId`'s actual result content — significantly more work for a benefit that only matters once the cheaper, more damaging "zero real calls at all" case (what actually got reproduced) is already closed. Left as a known, deliberately deferred gap rather than attempted under time pressure and silently left incomplete.

`missingInputs` stays unverified, and deliberately so: unlike "was this tool called", "does the ticket genuinely lack an order id" isn't mechanically checkable without another model call, which conflicts with the gate's own "pure function, zero I/O" architecture. This is judged acceptable because `missingInputs` fails safe — it's the gate's highest-precedence rule and only ever escalates toward `needs_more_data`, never toward a false `resolved`.

Also out of scope here, and worth naming precisely rather than leaving as an implicit gap: ADR-0006 and CONTEXT.md's `Status` entry name "evidence is inconsistent" as its own independent `needs_human` trigger, distinct from confidence level. `deriveConfidence` has no code path that compares evidence items against each other for contradiction — it only counts verified evidence by source type. Real contradiction detection would need either raw structured tool-result data threaded into the gate (evidence items are free text summarized by the model, not the tools' structured output) or another model call to judge semantic consistency — both larger changes than fit alongside this fix. `CONTEXT.md`'s `Confidence` entry now says this explicitly, pointing here.
