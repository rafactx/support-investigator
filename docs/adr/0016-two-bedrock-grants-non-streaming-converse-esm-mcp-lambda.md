# Two separate `bedrock:InvokeModel` grants, `stream: false` on the Bedrock provider, ESM-only for the Support MCP Lambda, and a region-dropping env bug in `search_support_knowledge` — four deploy-time facts the first live `cdk deploy` surfaced that no prior ADR anticipated

Building the CDK stack + real AWS deploy inherited three already-written, uncommitted artifacts from an earlier pass: `infra/demo-key-authorizer.ts`, `infra/support-investigator-stack.test.ts`, and `src/mcp/lambda-handler.ts`. The stack implementation itself (`infra/support-investigator-stack.ts`) and the CDK app entrypoint (`infra/main.ts`) didn't exist yet — writing them, then actually running `cdk deploy` against the target account (redacted — see `infra/main.ts`, `CDK_ACCOUNT_ID`; `us-east-2`) rather than stopping at a clean `cdk synth`, surfaced three facts none of the project spec, ADR-0002, or the pre-written stack test anticipated.

## The Support MCP Lambda needs its own Bedrock grant, separate from the Agent Lambda's

`search_support_knowledge` (`registerSearchSupportKnowledgeTool`, ADR-0009) always re-embeds its query with `index.provider` — the frozen `src/kb/data/index.json` was built with `bedrock-titan` — regardless of the Support MCP Lambda's own `EMBED_PROVIDER`. That means the Support MCP Lambda's execution role needs `bedrock:InvokeModel` on the Titan Embeddings model, independent of whatever the Agent Lambda needs for chat. The pre-written `support-investigator-stack.test.ts` had one test asserting *exactly one* `AWS::IAM::Policy` resource in the whole template carries any `bedrock:InvokeModel` statement — written before this cross-Lambda dependency was traced through, and directly incompatible with granting it correctly. The requirement's own wording only constrains "the agent Lambda's execution role", not the template as a whole, so the test was over-constrained relative to the requirement, not the requirement under-specified relative to the test. The test was rescoped to identify the Agent Lambda by a behavioral marker (the one function whose environment carries `SUPPORT_MCP_URL`) and assert only *that* role's policy set; a new test asserts the Support MCP Lambda's separate grant is scoped to only the Titan Embeddings foundation-model ARN, never the chat inference profile. Skipping this grant entirely would have made the flagship demo case (ADR-0006, ADR-0008 — the SKU-2002 stock/no-delivery ticket) silently degrade: `search_support_knowledge` would fail with `AccessDeniedException`, `evaluatePolicy` would treat that as a tool failure (ADR-0011) and always force `needs_human` regardless of the SKU evidence, hiding a permission gap behind a status that looks like a legitimate escalation.

## `BedrockModel` needs `stream: false`, or the deployed Agent Lambda 403s on every real investigation

`@strands-agents/sdk`'s `BedrockModel.stream()` defaults to Bedrock's `ConverseStream` operation (`ConverseStreamCommand`), which IAM gates behind `bedrock:InvokeModelWithResponseStream` — a different action from the plain `Converse` operation's `bedrock:InvokeModel`. `src/model/create-model.ts` (built earlier, never exercised against a real deployed Lambda until now) didn't set this, so the first live `POST /investigate` call against the deployed stack failed with `AccessDeniedException: ... not authorized to perform: bedrock:InvokeModelWithResponseStream ... because no identity-based policy allows [it]` — confirmed live, not inferred. The deploy requirement ("scoped to only `bedrock:InvokeModel` ... no broader policy") and the project spec's own Out-of-Scope list ("no response streaming (Lambda + demo-risk reasons)") already commit to a non-streaming Agent API; `stream: false` in `createModel` (`src/model/create-model.ts`) makes both of those true at the same time, by construction, rather than by widening the IAM grant to include `InvokeModelWithResponseStream` and only incidentally matching the "no streaming" decision. `create-model.test.ts` asserts on `BedrockModel.getConfig().stream` — a genuine public interface the SDK exposes for exactly this kind of configuration assertion, not an internal implementation detail.

## The Titan grant was unreachable until a pre-existing `us-east-1`-only bug in `search_support_knowledge` was fixed

The two grants above being individually correct wasn't sufficient proof the deployed stack actually worked: the first live `search_support_knowledge` call through the (public, unauthenticated at the time) `/mcp` route still failed with `AccessDeniedException`, naming a `us-east-1` foundation-model ARN — a different region from the `us-east-2` grant just added. The cause was in `registerSearchSupportKnowledgeTool` (from the knowledge-base pipeline, pre-dating the deploy entirely): it called `createEmbedProvider({ EMBED_PROVIDER: index.provider })` — a *freshly constructed* env object carrying only `EMBED_PROVIDER`, discarding every other real env var including `AWS_REGION`. `createBedrockTitanEmbedProvider(env)` then fell back to its own `region: env.AWS_REGION ?? 'us-east-1'` default, silently pointing every Titan Embeddings call at `us-east-1` regardless of which region the Lambda was actually deployed to. This had no way to surface before now: fixture-mode CI evals never select `bedrock-titan` at all (`EMBED_PROVIDER=fake`), and nothing earlier ran the Support MCP anywhere other than a developer's own machine (where `AWS_REGION` is typically unset entirely, or happens to be `us-east-1`). The fix — extracted as `buildQueryEmbedEnv`, a pure function spreading the real env before overriding only `EMBED_PROVIDER` — is a regression fix to the knowledge-base pipeline's own code, made here because the live deploy is what finally exercised the code path that exposes it, and because ADR-0009's own guarantee ("always re-embedding the query with the same provider the index itself was built with") is meaningless if the provider it builds silently targets the wrong region. Re-running the flagship demo ticket (ADR-0006, ADR-0008) after this fix produced exactly the documented case: `proposed.diagnosis.confidence: "high"` (the model's own overconfidence, ADR-0010's own named finding) corrected by the gate to `final.diagnosis.confidence: "medium"` / `status: "needs_human"` — the auditable `proposed` vs `final` divergence CONTEXT.md's own entry on that pairing describes, observed live for the first time.

## Deferred: locking `/investigate`'s CORS to the CloudFront domain

ADR-0014 names the deploy as the work that would design the deployed SPA's cross-origin access to the Agent API ("the deployed SPA's cross-origin request to the Agent API has no working local analogue to copy from — it has to be designed then, not inferred from this dev-only workaround"). The deploy's own acceptance criteria don't mention CORS, S3, or CloudFront — only the two Lambdas and the API Gateway in front of them — and no CloudFront distribution exists yet in this stack or anywhere else in the repo (SPA hosting isn't scoped yet). `SupportInvestigatorStack`'s `HttpApi` is therefore built with no CORS configuration at all: there is no CloudFront domain yet to lock it to, and adding a permissive placeholder now would just be a second decision for whichever change actually deploys the SPA to immediately narrow. This ADR is the forward pointer ADR-0014 asked for, deferring to that future change rather than resolving it here.

## The Support MCP Lambda bundles as ESM; the Agent Lambda and demo-key authorizer stay CJS

`loadKnowledgeIndex`'s `DEFAULT_INDEX_PATH` resolves `src/kb/data/index.json` relative to the bundled file's own `import.meta.url`. esbuild only makes `import.meta.url` resolve to a real value when the output format is ESM — under CJS it evaluates to `undefined` (esbuild's own `empty-import-meta` warning), which would make every cold start of the Support MCP Lambda fail to find the frozen index. But ESM output introduced a second problem: `@modelcontextprotocol/sdk` depends on `cross-spawn` (for its stdio transport, which this project never uses — only Streamable HTTP, ADR-0007), and cross-spawn's CJS internals call `require()` in a way esbuild's ESM bundle output can't statically resolve, throwing `Dynamic require of "child_process" is not supported` at cold start — reproduced live on the first deploy attempt, well before knowledge-index loading was ever reached. Rather than rewriting `load-index.ts` to avoid `import.meta.url` (which would cost it correctness under Node's own native ESM execution — the same runtime `pnpm dev` and every test file already use), the Support MCP Lambda's `NodejsFunction` bundling config sets `format: OutputFormat.ESM` plus a banner (`import { createRequire } from 'module'; const require = createRequire(import.meta.url);`) — the standard esbuild/Lambda-ESM fix that gives bundled CJS dependencies a working `require` again. The Agent Lambda and demo-key authorizer have no `import.meta.url` dependency, so they stay on esbuild's CJS default, which sidesteps the cross-spawn problem entirely (real `require` is just available, no shim needed) — the two Lambdas deliberately don't share one bundling format.
