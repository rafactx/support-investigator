# `KnowledgeIndex` pins its own embed provider; `search_support_knowledge` always queries with it, never with the ambient `EMBED_PROVIDER`

> **Scope after the focused-slice decisions:** this remains valid for the optional documentary search capability. The Knowledge Index is not on the Finding decision path and does not select the normative Finding Source Pack; a retrieval result cannot become a Ledger Fact or satisfy an Evidence Contract.

Building the knowledge-base pipeline required deciding how `search_support_knowledge` picks the `EmbedProvider` it uses to embed an incoming query. The obvious reading of the project spec's config table — `EMBED_PROVIDER` selects the provider, so the running process's env var should govern every embedding call, build-time and runtime alike — breaks the moment `kb:refresh` is ever run with a different provider than the one currently exported in the shell: a `bedrock-titan`-built index (1024→256-dim Titan vectors) queried with a `fake` (256-dim hashing) or `local` (384-dim MiniLM) embedding produces a cosine score between two unrelated vector spaces — not a low-relevance score, a meaningless one, and a dimension mismatch would 500 outright once the vector lengths stop lining up.

We chose to record `provider`, `model`, and `dimensions` directly on the frozen `KnowledgeIndex` (`src/kb/types.ts`) and have `search_support_knowledge` build its query-time `EmbedProvider` from `index.provider`, not from `process.env.EMBED_PROVIDER`. `searchSupportKnowledge` (`src/kb/search.ts`) additionally refuses up front — throws, doesn't silently degrade — if it's ever called with a provider whose `id`/`dimensions` don't match the index it's searching. `EMBED_PROVIDER` still governs `kb:refresh` (which provider embeds the corpus), but once an index is built, querying it is no longer a runtime configuration choice; it's a fact about that specific frozen artifact, the same way a `git commit`'s SHA isn't reconfigurable after the fact.

This made the CI-default `fake` provider's own design a load-bearing decision rather than an incidental one: acceptance criterion 5 ("unit tests cover retrieval relevance for 2-3 representative queries against the frozen fixture index") can only be a real test if `fake`'s similarity scores are driven by actual lexical content, not by an opaque per-string hash. `createFakeEmbedProvider` (`src/kb/embeddings/fake-embed-provider.ts`) is therefore a deterministic hashing-trick bag-of-words embedder — each token hashes into one of 256 buckets, the resulting vector is L2-normalized — rather than a random or constant stub. `src/kb/search.test.ts`'s three relevance assertions against `src/kb/fixtures/knowledge-index.fixture.ts` (a small, hand-written, topic-distinct fixture corpus, same fixture-first shape as `gateway/fixtures/` under `ADR-0005`) genuinely fail if the ranking logic breaks, not just when the fixture data changes.
