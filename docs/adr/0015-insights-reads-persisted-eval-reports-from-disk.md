# `pnpm insights` reads persisted `final`-only eval reports from disk, gitignored, no dedupe across sources

Building `pnpm insights` required deciding what "`pnpm insights` reads the structured outputs already produced by `pnpm evals` / `pnpm evals:live` runs" actually means in code — neither command persisted anything before this; both only printed a report to the console (`run-evals.ts`/`run-evals-live.ts`'s `printReport`). Two ways to close that gap were available: have `insights` re-run the agent against the golden tickets itself, or have the two existing eval entrypoints write their results to disk and have `insights` read them back. We chose the second. Re-running the agent would have duplicated `runEvalSuite`'s own orchestration inside a third command and contradicts `ADR-0004`'s explicit boundary ("no new ML or analytics infrastructure... rather than building new... infrastructure") — `insights` is aggregation over already-produced data, not a third way to produce it.

`writeEvalReport` (`src/evals/eval-report.ts`) persists one `TicketEvalResult[]` per run to `reports/evals.json` (`pnpm evals`) or `reports/evals-live.json` (`pnpm evals:live`), each call from the run's own entrypoint (not from `runEvalSuite` itself, which `run-eval-suite.test.ts` also calls directly in `vitest run` — writing from inside `runEvalSuite` would make every unit test run silently overwrite the real report on disk). Each persisted record keeps only `{ ticketId, final }`, not the full `TicketEvalResult`: `final` is the policy gate's verdict (`ADR-0006`/`ADR-0010`), the only status/diagnosis this project treats as authoritative, and none of the insights requirements need `proposed` or `activity` — carrying them would be data the aggregation never reads, just more surface for the schema to drift out of sync with. `pnpm evals` writes its report unconditionally, even when a ticket assertion fails — a red run still produced real `final` results worth surfacing, and gating persistence on `passed` would make a broken suite's own patterns invisible to the tool meant to surface patterns.

`reports/` is gitignored, not committed. This is the opposite call from the Knowledge Index (`src/kb/data/index.json`, deliberately committed so content drift is reviewable in a diff, `ADR-0009`) — the discriminating question is whether anything downstream depends on the file existing without its producer having run first. Nothing does: `pnpm insights` is only ever meaningful after `pnpm evals`, there is no CI workflow in this repo that reads a report without also being able to regenerate it, and the report is fully deterministic from `GOLDEN_TICKETS` plus (for `evals:live`) a live model call — reproducible, not source-of-truth data that would silently rot if not captured. This is the same treatment as `dist/`/`cdk.out/`, a regenerable build artifact, not the same treatment as the frozen index.

`computeInsights` (`src/insights/compute-insights.ts`) pools records from every report given without deduplicating by `ticketId` across `evals` and `evals:live` — the two are independent observations of the same golden tickets (one scripted, one against a real model), not one dataset with a duplicate to remove; a ticket appearing in both sources legitimately counts twice. Grouping (diagnosis hypotheses, missing inputs) is exact-string only, no normalization, stemming, or clustering — `ADR-0004`'s "no new ML or analytics infrastructure" rules that out directly, and the real 15-golden-ticket run's output (three `permission-403` tickets sharing one hypothesis verbatim, twelve singletons) shows exact-string grouping already surfaces the intended pattern without it. "Escalation rate by category" is computed as each status's share of *all* investigations read (`count / investigationCount`), not a share of escalations only — the ambiguity is real (both readings are defensible), but printing both the count and the total (`4/15 (26.7%)`) in `formatInsightsReport`'s output makes the number legible under either interpretation, and a reader is never left to guess the denominator.
