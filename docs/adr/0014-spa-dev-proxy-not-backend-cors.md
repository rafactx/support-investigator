# Local-dev SPA reaches the Agent API through Vite's dev proxy, not backend CORS headers

Building the evidence-timeline SPA required deciding how the browser, running on Vite's dev origin (`http://localhost:5173`), reaches the Agent API's `POST /investigate` on its own origin (`http://localhost:8787`, `pnpm dev serve`). The obvious approach — call `http://localhost:8787/investigate` directly from the browser with `fetch` — fails immediately: `createInvestigateApp` (`src/api/app.ts`) sets no CORS headers, so the browser blocks the cross-origin request before it ever reaches the server (`TypeError: Failed to fetch`), confirmed live against the real local stack while building the SPA, not assumed from reading the code.

Two ways to close that gap were available: add CORS middleware to `createInvestigateApp` (e.g. `hono/cors`, permissive locally), or configure Vite's own dev-server proxy (`server.proxy`) to forward `/investigate` to the local Agent API, making the browser's request same-origin instead. We chose the proxy. The project's security requirements already assign CORS a specific, narrower shape for the *deployed* stack — "API Gateway + `x-demo-key` header + CORS locked to the CloudFront domain" — and that belongs to the CDK stack + real AWS deploy, not the SPA. Adding CORS middleware to `src/api/app.ts` now would have meant either shipping a permissive dev-only CORS policy that the deploy work has to immediately narrow (a decision made twice, in two changes, on the same file), or trying to anticipate the deploy's exact allowed-origin list from inside frontend work that has no CDK stack to reference yet. The proxy keeps the fix entirely inside `web/` — and leaves `src/api/app.ts` untouched.

`vite.config.ts`'s `server.proxy` maps `/investigate` to `http://localhost:8787`; `App.tsx`'s `API_BASE_URL` defaults to `''` (not `'http://localhost:8787'`), so `submitInvestigation` requests the relative path `/investigate`, which only resolves through the dev-server proxy — the same built bundle picks up a real, deployed API URL later via `VITE_API_URL` at build/deploy time, at which point the browser calls that URL directly and the deployed stack's own CORS configuration (not this proxy, which only exists in `vite dev`) is what has to make that cross-origin call succeed. This ADR is the forward pointer for whoever builds the deploy: the deployed SPA's cross-origin request to the Agent API has no working local analogue to copy from — it has to be designed then, not inferred from this dev-only workaround.
