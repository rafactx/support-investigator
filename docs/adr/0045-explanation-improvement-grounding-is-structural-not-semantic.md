# Explanation improvement grounding is structural, not semantic — and a Bedrock failure is never committed to the Audit Trail

The explanation-improvement feature needed a Bedrock-improved explanation that "must remain grounded exclusively in confirmed normalized intake, the Evidence Ledger, contract result, deterministic judgment and the pinned Finding Source Pack" and where "unsupported claims or citations reject the improved explanation." Verifying that an arbitrary free-text claim is true against a set of facts is an open NLP problem this project has no business half-solving. `domain/explanation-improvement.ts` instead makes fabrication *structurally* impossible rather than *detecting* it after the fact, the same move `bedrock-language-assistance.ts`'s `buildIntakeExtractionSchema` already makes for Account Scope ("it structurally cannot appear in a model proposal"): `buildExplanationImprovementRequest` sends the model only placeholder *names* (`"skuId"`, `"destinationPostalCode"`, …) drawn from `buildAllowedPlaceholders`, never their real values. The model must write `{{skuId}}` to reference the SKU — it has no real SKU string to retype, copy, or hallucinate a variant of. `checkExplanationGrounding` then verifies, deterministically: every `{{placeholder}}` used is one that was actually offered; no digit survives once every placeholder is stripped out (so a raw, unbracketed number is rejected the same way an unknown placeholder is); and every cited URL is a member of `findingSourcePack(findingCode)`. Only after every check passes are real values substituted back in.

This is deliberately a narrower claim than the requirement that "every factual claim is derivable from the allowed inputs." The check proves the summary introduces no identifier, citation or number this Investigation didn't already produce; it cannot prove a claim built entirely from allowed placeholders and plain wording is *semantically true* (a summary could still reorder correct facts into a misleading sentence). Full semantic verification would need either a second model call to grade the first — trading one unverified generation for two — or a hand-built claim-extraction grammar disproportionate to a single-Finding-Code slice. The structural check is the honest, provable subset of that requirement this change implements; wider claim-derivability is out of scope until (if ever) the Finding taxonomy grows enough sources per Finding Code to make citation checking alone insufficient.

`ExplanationImprovementOutcome` (`domain/investigation.ts`) is two-valued — `accepted` | `rejected` — not three. A Bedrock/provider failure (`LanguageAssistance.improveExplanation` reporting `kind: 'unavailable'`) never reaches an `ExplanationImprovementOutcome` at all: `investigations-app.ts`'s route returns `503` directly and never calls `repository.requestExplanationImprovement`, so nothing is appended to the Investigation Audit Trail and `revision` does not move. A `rejected` grounding failure, by contrast, *is* a real domain event — Language Assistance did run, on real facts, and produced something the deterministic gate refused — so it commits an `explanation_improvement_requested` event and bumps `revision` the same as an `accepted` one. The distinction matters for the retry UX: a transient Bedrock outage should let N2's next click attempt the call again at the same `expectedRevision`, not force a revision-aware retry of a failure that was never really "the Investigation's" event to begin with.

## Consequences

`InvestigationOutcome.explanationImprovement` is intentionally not carried forward when a later `intake_updated` event recomputes `outcome` via `buildInvestigationOutcome` (`POST`/`PATCH`'s shared `runPlaybookAndDecideOutcome`). A prior improvement was grounded in the specific Finding/Decision/Ledger that outcome held; if intake correction changes any of those, the old improvement would misattribute wording to a Finding it was never generated against. This isn't a special case in `foldInvestigationEvents` — it falls out for free because `buildInvestigationOutcome` never knows about a prior `explanationImprovement` to preserve, and `explanation_improvement_requested`'s own fold only ever merges onto whatever `outcome` already exists at that point in history (`src/domain/investigation.test.ts`'s "a later intake_updated event drops…" test pins this).

The placeholder-name-only design costs prose flexibility: the model cannot phrase a sentence that interleaves a real value with its own wording the way free substitution would allow, and a legitimate but coincidentally digit-bearing phrase (a duration, a step number) is rejected the same as a fabricated one. `finding-source-pack.ts`'s deterministic `summaryFor()` output is already digit-free generic prose per `DecisionReason`, so `deterministicSummary` given to the model as tone reference never leaks a real value through that channel either — the model is never shown a real identifier anywhere in the request, not just told not to write one.
