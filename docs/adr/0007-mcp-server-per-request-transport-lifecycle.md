# Support MCP's Streamable HTTP transport: fresh `McpServer` + `StreamableHTTPServerTransport` per HTTP request, not one long-lived pair

> **Status: superseded for the target architecture by ADR-0039.** This remains the record of the correct workaround for the implemented MCP TypeScript SDK v1 prototype. The focused slice migrates to the v2 server and Hono packages, whose `createMcpHandler` owns the per-request stateless Web Standard transport lifecycle.

Building the Support MCP server (Streamable HTTP, `get_order_context`) required deciding how a `StreamableHTTPServerTransport` in stateless mode (`sessionIdGenerator: undefined`) is meant to be wired to a plain `node:http` server. The obvious design — construct one `McpServer` and one `StreamableHTTPServerTransport`, `connect()` once at process startup, then call `transport.handleRequest(req, res)` for every incoming request — fails: the first request (the client's `initialize` call) succeeds, but the second request (the `notifications/initialized` notification Strands' `McpClient` sends immediately after) gets a `500` from `transport.handleRequest`, which surfaces to the client as `StreamableHTTPError: Streamable HTTP error: Error POSTing to endpoint:` and aborts `McpClient.connect()`. Reproduced directly against the MCP SDK's own `Client`/`StreamableHTTPClientTransport` (bypassing Strands entirely) to confirm this is a transport-layer fact, not a Strands integration bug.

The SDK's own `dist/esm/examples/server/simpleStatelessStreamableHttp.js` does something less obvious: it builds a **brand-new** `McpServer` and `StreamableHTTPServerTransport` **inside the request handler, on every single request**, `connect()`s them, handles that one request, and lets them get garbage-collected (`res.on('close', ...)` closes both). This works because each Streamable HTTP request stands alone at the protocol level — there is no requirement that the same server object see the same client's `initialize` and subsequent calls, only that *some* correctly-initialized `McpServer` handles each request. Verified empirically: switching to the per-request pattern fixed `connect()`, `listTools()`, and `callTool()` end to end (see `src/mcp/server.test.ts`, exercised through Strands' real `McpClient`, not a mock).

We adopted the per-request pattern (`src/mcp/server.ts`) rather than debugging why the persistent-transport form breaks internally. Two reasons: it's what the SDK's own maintainers ship as the reference implementation for stateless mode, and it's *also* what the Lambda deployment needs regardless — a Lambda invocation cannot rely on any state (including an already-connected transport) surviving between invocations. Building the CLI/local-dev server around the same lifecycle now means the Lambda deployment reuses `startSupportMcpHttpServer`'s request-handling shape almost unchanged instead of needing a second implementation for Lambda.

This resolves the main unproven technical risk of the MCP integration: Strands' `McpClient` **does** work against a real Support MCP server over Streamable HTTP — provided the server-side transport lifecycle matches the SDK's stateless pattern.
