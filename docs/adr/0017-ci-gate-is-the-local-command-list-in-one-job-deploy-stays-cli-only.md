# CI gate is the same 5 local commands, in one job; introducing Biome for `lint`; no GitHub Actions deploy workflow added

The CI requirements named `typecheck`, `lint`, unit tests, `pnpm evals`, and `cdk synth` as the required PR gate. Two things needed a decision that no prior ADR covers: what `lint` actually runs (no lint tool was installed anywhere in the repo before this change), and whether the requirements' `workflow_dispatch` parenthetical means building a GitHub Actions deploy workflow that didn't exist before either.

## `lint` is Biome, linter-only, not `biome check`

The original project spec already named Biome ("Testing/lint: Vitest + Biome") as the intended tool, but nothing before this change installed it — there's no lint tooling anywhere in the repo prior to this change. Running `biome check .` (formatter + linter combined) against the untouched codebase produced 8,067 errors and 17,070 warnings, almost entirely formatting diffs (tabs vs the repo's actual 2-space/single-quote style) across every file the project has ever written. Reformatting the whole repo inside this diff would have buried the actual CI change and made its own self-review meaningless — a Divergent Change smell turned up to eleven. `biome lint .` (linter rules only, no formatter) against the same codebase produced exactly 1 error and 11 warnings; the linter and the codebase already mostly agree. `pnpm lint` therefore runs `biome lint .`, not `biome check .`. `biome.json`'s `formatter` block is still configured correctly (2-space, single-quote, matching the codebase's actual style) for editor integration, but the CI gate never invokes it — a repo-wide reformat is a separate, deliberate future change, not a side effect of wiring up CI.

The one pre-existing lint error (`noUnsafeOptionalChaining` in `infra/support-investigator-stack.test.ts`, from the CDK deploy work) was fixed as part of this change — not because the CI work owns that file, but because a CI gate that's red on the commit that introduces it defeats the point of gating anything; `statements[0]` was already proven non-empty two lines above by `toHaveLength(1)`, so a non-null assertion is the correct fix, not a suppressed rule. `src/kb/data/index.json` (the frozen Knowledge Index artifact, CONTEXT.md) is excluded from Biome's `files.includes` — it's generated data, not hand-written source, and exceeds Biome's default 1 MiB file-size limit. The remaining 11 warnings (`noNonNullAssertion` in pre-existing gateway/embedding code) are left as warnings: Biome's recommended preset treats them as non-blocking by design, and silently rewriting code this change doesn't own to chase a clean `biome check` output would be scope creep beyond what the gate needs.

## No GitHub Actions deploy workflow — the manual-deploy requirement is satisfied by an absence, not a new automation path

The project spec's architecture block and the CI requirements both use the phrase "manual (`workflow_dispatch`)" to describe deploy. The first draft of this change read that literally and built a second `.github/workflows/deploy.yml` (`workflow_dispatch`-triggered, calling `cdk deploy` via `aws-actions/configure-aws-credentials` against a not-yet-configured `AWS_DEPLOY_ROLE_ARN` secret). On self-review this was reverted: ADR-0002 — the ADR the requirement itself defers to ("per ADR-0002") — describes deploy as a real `cdk deploy` run from a developer's own machine through a dedicated deploy IAM user, never mentions GitHub Actions, and that path was already executed for real against the target account (redacted — see `infra/main.ts`, `CDK_ACCOUNT_ID`; `us-east-2`) — see `docs/runbooks/cdk-destroy.md`. No OIDC role or deploy secret exists in this repo, and nothing asks to configure one. A `deploy.yml` that can never actually run (missing secret, no configured trust policy) is Speculative Generality: an abstraction built for a need the spec doesn't have, that would sit in the repo looking like working automation while being unrunnable.

The requirement is instead satisfied the way its own wording supports just as well: `workflow_dispatch` describes deploy's already-decided manual character (ADR-0002's CLI path), and "CI never auto-deploys" is a property of the one workflow this change does add. `.github/workflows/ci-workflow.test.ts` proves it two ways — no step anywhere in `ci.yml` runs `cdk deploy`, and `ci.yml`'s `on` keys are a subset of `{push, pull_request}`, so no trigger type that could ever fire a deploy (`workflow_dispatch`, `schedule`, `workflow_run`) exists in this workflow at all. If a future change wants deploy triggerable from GitHub Actions instead of a developer's CLI, that's a real, separate architectural decision (an OIDC trust policy, a new IAM role, a secret) — not one to make by writing an unrunnable file to satisfy a parenthetical.

## The gate is one job, sequential steps, matching local dev exactly

`ci.yml` runs `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm evals`, `pnpm cdk synth` as five sequential steps in a single `gate` job — the same five commands, in the same order, a developer already runs locally per the project spec's own CI description (`typecheck → lint → unit → evals → cdk synth`). No matrix, no parallel jobs: nothing in the CI requirements asks for OS/Node-version coverage, and splitting five fast, deterministic, credential-free commands across jobs would only add scheduling overhead for no signal this project needs. `pnpm evals` already includes the sabotage regression (`sabotage-check`, wired in by the eval harness) as one of its 15 golden-ticket assertions — there's no separate "sabotage" step to add. Both `pnpm evals` and `pnpm cdk synth` were confirmed to run without any AWS credentials present (env stripped of every `AWS_*` variable, `AWS_CONFIG_FILE`/`AWS_SHARED_CREDENTIALS_FILE` pointed at `/dev/null`) before being wired into the gate — `infra/main.ts` hardcodes the target account/region rather than reading `CDK_DEFAULT_ACCOUNT`, and neither eval fixtures nor `cdk synth` reach out to AWS.

`push: branches: [main]` was added alongside `pull_request` — not asked for directly, but required for the README status badge to work at all: a GitHub Actions status badge renders the *default branch's* latest run, and a `pull_request`-only trigger never produces a run on `main`, so the badge would permanently read "no status". `concurrency: { group: ci-${{ github.ref }}, cancel-in-progress: true }` was added as one-line badge hygiene — without it, an in-flight run from an earlier push could still be running (and later report status) after a newer push's run starts, occasionally putting a stale result behind the badge; this is cheap enough not to warrant its own ADR paragraph, but it's called out here so it doesn't read as an unexplained addition in the diff.
