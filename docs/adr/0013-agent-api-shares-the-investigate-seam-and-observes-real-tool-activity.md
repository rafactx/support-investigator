# `POST /investigate` shares one `investigateTicket` seam with `pnpm dev investigate`, which now also observes real tool activity instead of assuming none failed

Building the Agent API's `POST /investigate` handler required deciding how much of `cli.ts`'s existing `runInvestigateCommand` — build an `Agent` with `structuredOutputSchema`, call `agent.invoke()`, run `evaluatePolicy` over the result — the new HTTP route should duplicate versus reuse. Copying that logic into `src/api/app.ts` would have been the fastest path, but it's exactly the shape ADR-0006/ADR-0010's own precedent argues against: two call sites computing the same `{ proposed, final }` envelope independently is a place a future policy-gate change (a new required field, a new rule) could easily get applied to one and not the other without either test suite catching it.

We extracted `investigateTicket` (`src/agent/investigate.ts`) as the one investigation seam both `cli.ts`'s `runInvestigateCommand` and `src/api/app.ts`'s `POST /investigate` route call. While doing this, `cli.ts`'s own doc comment surfaced a stale deferral: `runInvestigateCommand` passed `toolFailures: []` to `evaluatePolicy` unconditionally, with a comment attributing the gap to the eval harness — but the eval harness had already built exactly the observer that gap named, `extractToolActivity` (`src/agent/tool-activity.ts`, née `src/evals/tool-activity.ts`), and wiring it only into `run-eval-suite.ts`. That left `pnpm dev investigate` and (absent this decision) the new API route both structurally unable to honor ADR-0006's rule 2 ("a required tool failed → `needs_human`, unconditionally") — a real 403 from, say, `ORDER-4031` would have produced a `final` that never escalates, in production, not just in a stale doc comment. `investigateTicket` now calls `extractToolActivity(agent.messages)` and feeds its real `toolFailures` into `evaluatePolicy`, closing that gap in both callers at once rather than only in the new one.

This moved `extractToolActivity` out of `src/evals/`: it's reached from the real `POST /investigate` request path now, not just the eval harness, and its only tie to `evals/` was importing `STRUCTURED_OUTPUT_TOOL_NAME` from `fake-model.ts` — a test double. That constant now lives in `src/agent/structured-output-tool-name.ts`; `fake-model.ts` re-exports it for its own existing importers. The alternative (leave `tool-activity.ts` in `evals/`, have `src/agent/investigate.ts` import from there) would have made the production module graph reach into a directory whose other contents are exclusively test doubles and CI-gating code — a smell worth avoiding at the point of introduction rather than accepting for one ticket and cleaning up later.

**Request payload.** `POST /investigate` accepts `{ ticketText: string }` — one free-text field, not separate `orderId`/`skuId`/etc. fields. This matches the shape `GoldenTicket.ticketText` and `pnpm dev investigate`'s CLI argument already use: `INVESTIGATE_SYSTEM_PROMPT` instructs the model to extract each tool's own inputs from the ticket text itself. Structured fields would have required editing that prompt, and `pnpm evals`'s `FakeScriptedModel` never reads message text at all (it advances a fixed script regardless of what the agent was asked) — a prompt change made for this ticket would have been invisible to the CI gate that's supposed to catch prompt regressions. Not changing the prompt was the safer default.

**Lambda-compatible, deployed nowhere yet.** `src/api/app.ts`'s `createInvestigateApp(deps)` is a plain `Hono` app builder with no I/O of its own (no env reads, no server startup) — the same instance `cli.ts`'s new `serve` command wraps with `@hono/node-server` locally and `src/api/lambda-handler.ts` wraps with `hono/aws-lambda`'s `handle()` for API Gateway. The Lambda handler's deps read one new env var, `SUPPORT_MCP_URL` — the architecture diagram (Agent API Lambda → `McpClient` → Support MCP Lambda) made concrete, the production analogue of `cli.ts`'s locally-started `startSupportMcpHttpServer`. Provisioning that URL, and the Support MCP Lambda itself, belongs to the CDK deploy work, not this decision ("no AWS resources provisioned yet") — `createLambdaDeps` throws when it's absent, and does so lazily on first invocation rather than at module load, so importing `lambda-handler.ts` (as its own test file does, to reach `createInvestigateLambdaHandler` with fixture deps) never fails just because the env var isn't set yet.

**Local dev entrypoint.** `pnpm dev serve [port]` was added to `cli.ts`'s existing command dispatcher rather than a second script/entrypoint file, so "runs locally via `pnpm dev`" stays literally true and the "reproducible in two commands" framing for `pnpm dev` isn't quietly forked into two different local dev commands for two different purposes. Unlike every other `pnpm dev` command, `serve` is long-lived: it does not disconnect its `McpClient` or close its Support MCP server after one request, only on `SIGINT`/`SIGTERM`.
